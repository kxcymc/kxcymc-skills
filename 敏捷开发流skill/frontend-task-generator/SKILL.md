description: 分析 需求文档、后端技术方案和现有前端代码，生成高度结构化、可直接落地的标准化前端需求开发任务清单。
---

### 基本规则
- 本 Skill 在做：输入需求文档、后端技术方案和现有的前端代码，输出一个标准化的前端开发任务拆解文档。
- 任务拆解应高度结构化，1 个 task 对应 1 块 UI 或 1 组强相关文件。
- 必须包含：约定（如 D2C/UI 规范）、当前代码差异、接口策略、以及具体的 Task 列表。
- 每个 Task 必须包含固定要素：设计稿输入、落地文件、数据源、复用点、完成标准。
- 保持客观中立的表述，聚焦于需要“修改代码”的本质动作。不相关或纯后端的改动应被剔除。

---

### 执行步骤

**Step 1: 收集关键入参**
如果用户触发了本 Skill 但未提供足够信息，你需要主动询问或使用对应工具（如 `lark-doc` 提取飞书文档内容）收集以下“入参”：
1. **需求文档 链接或文档内容**（必填，用于理解业务需求和 UI/交互逻辑）。
2. **后端方案链接或接口契约**（必填，用于明确前后端数据交互和职责边界）。
3. **前端目标代码文件路径**（必填，用于对比现状，确认已有能力和缺失点）。
4. **设计稿（Figma）链接**（选填，用于任务中的“设计稿输入”关联）。
5. **项目约定与技术栈约束**（选填，如 React、SCSS 规范、特定的基础组件库等，未提供则使用默认约定）。

**Step 2: 分析现状与需求差异**
- 使用 `Read` 工具读取前端代码文件。
- 将 需求文档 与后端方案的内容进行交叉比对，识别“必须由前端修改的点”和“后端已处理、前端无需修改的点”。
- 梳理当前的组件状态，找出“当前代码差异”（即哪些模块缺失、哪些字段未消费、哪些逻辑需要下线）。

**Step 3: 制定全局策略**
- 总结“约定”，明确使用的基础组件库、样式方案、复用策略等。
- 明确“接口策略”，判断哪些接口走真实联调，哪些需要 mock 兜底。

**Step 4: 生成标准化 Task 清单**
使用以下 Markdown 结构生成最终结果（必须严格遵循）：

```markdown
# [需求名称] 任务拆解

## 约定 
- [前端技术栈、样式方案、通用组件复用规则等]
- 无设计稿的 Task, 直接在代码中实现。
- 有设计稿的 Task, 调用 `ecom-d2c` skill 进行实现。

## 当前代码差异
- [现状描述，例如：现有组件仅包含 A，未包含 B；某路由仍未注册等]

## 接口策略
- 继续走真实接口：[接口列表]
- 仅对新增模块或未就绪字段使用 mock 数据：[接口列表]
- mock 数据统一存放在该 Task 所对应的核心组件目录下，命名为 `mock.ts`（例如：`src/pages/Xxx/components/Yyy/mock.ts`）。

## Task 1：[具体任务名称，例如：下线 XxxXxxx，改为yyyYYyyy]
- 设计稿输入：[Figma 链接或描述]
- 落地文件：[涉及的前端代码路径列表]
- 数据源：[依赖的接口名或 mock 路径]
- 复用点：[可复用的基础组件或现有逻辑]

## Task 2：[具体任务名称]
... (同上)
```

---

### 用户交互策略
- 优先验证用户提供的链接是否能正常访问。如果遇到飞书文档，主动提示用户你将使用 `lark-doc` 去读取内容。
- 如果代码路径过于模糊，建议用户提供精确的文件名或使用 `SearchCodebase` / `Glob` 辅助查找。
- 最终输出必须是一个markdown文件，放在工作区根目录下即可。

---

### 核心约束
- 每个 Task 拆分粒度应适中，通常 1 个 Task 对应 1 个页面级组件、一个通用组件的升级，或者一类相关的状态管理变更。
- 每个 Task 需要改动的文件必须都互不相同。
- **只列出前端改动点**。后端的数据库修改、单纯的后端配置变更等不要作为前端 Task 列出。
- 输出格式必须与上述 Markdown 模板保持一致。
- 最终输出必须是中文。
