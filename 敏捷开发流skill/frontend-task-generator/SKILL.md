### 基本规则

- 本 Skill 的输入为需求文档、后端技术方案和现有前端代码，输出为一份标准化的前端开发任务拆解文档。
- 任务拆解保持高度结构化，1 个 Task 对应 1 块 UI 或 1 组强相关文件。
- 文档包含四个固定章节：约定（含 UI/D2C 规范）、当前代码差异、接口策略、Task 列表。
- 每个 Task 包含固定要素：设计稿输入、落地文件、数据源、需求新增逻辑和样式、现有逻辑和样式变更。
- 表述客观中立，聚焦于需要修改前端代码的本质动作；清单内容限定在前端可落地的改动范围内。
- 本 Skill 的处理范围覆盖功能、UI、交互与接口逻辑；最终清单中的每个 Task 均属于功能/UI/接口类改动，埋点相关内容留给其他专用 Skill。

---

### 面向读者的表述要求

文档面向他人阅读，读者仅凭本文档即可掌握完整改动信息。遵循以下要求：

- **引用具体到可定位对象**：凡引用需求或后端方案的内容，摘录原文关键句，并标注具体出处（页面名、路由、接口名、字段名、章节标题）。引用一律落到可定位的对象上。
- **用自然语言描述需求点**：把理解到的需求点完整写出来，正文以文字表达为主；出处以文字标注（页面名、路由、接口名、字段名、章节标题），不附需求文档、技术文档等的链接。
- **Task 关联需求条目**：需求点逐条编号，每个 Task 关联到对应的需求条目编号。
- **保留单一最新结论**：当结论发生更新时，将文档中被替代的旧表述整体替换为最新结论，全篇保持单一、一致的结论。

### 执行步骤

**Step 1: 收集关键入参**

当已有信息尚需补充时，主动通过提问或工具（如 `lark-doc` 提取飞书文档内容）收集以下入参：

1. **需求文档链接或内容**（必填，用于理解业务需求和 UI/交互逻辑）。
2. **后端方案链接或接口契约**（必填，用于明确前后端数据交互和职责边界）。
3. **前端目标代码文件路径**（必填，用于对比现状，确认已具备能力和待补齐差异项）。
4. **设计稿（Figma）链接**（选填，用于任务中的“设计稿输入”关联）。
5. **项目约定与技术栈约束**（选填，如 React、SCSS 规范、基础组件库等；缺省时采用项目默认约定）。

**Step 2: 分析现状与需求差异**

- 使用 `Read` 工具读取前端代码文件，掌握组件现状。
- 将需求文档与后端方案交叉比对，识别“需要前端改动的点”与“后端已覆盖、前端保持现状的点”。
- 梳理组件现状，明确列出两类结论：**项目已具备的能力**、**仍待补齐的差异项**（例如待新增的模块、尚待消费的字段、待替换、待删除等等的逻辑）。
- 结合接口响应字段的语义理解需求措辞。例如涉及“总数/总量/全部数量”的表述，对应接口返回的计数字段（如 `total`），据此确定首屏请求与分页策略。
- 埋点、数据上报、事件追踪相关章节留给其他专用 Skill；本 Skill 的分析结果覆盖功能/UI/接口范围。

**Step 3: 核对接口生成现状（基于事实）**

- 判断接口就绪度时，先读取项目内已生成的接口代码（如 BAM 自动生成的 service 与类型定义）。
- 以真实的方法签名、请求参数、响应字段为准，得出“接口已就绪”或“接口处于开发阶段”的结论。
- 入参结构、返回结构、调用方式均依据生成代码确认，保持与生成定义一致。

**Step 4: 制定全局策略**

- 总结“约定”：明确 UI 组件库、通用组件复用策略、样式规范等。
- 明确“接口策略”：
  - 存在已就绪的真实接口时，前端调用对应接口，并写明接口名与关键请求/响应字段。
  - 接口处于开发阶段时，前端以 mock 承接并预留切换点；mock 数据存放于该 Task 对应的核心组件目录，命名为 `mock.ts`。
  - 数据源、导出、上传等技术选型依据后端方案与项目既有能力确定，与后端职责边界保持一致。

**Step 5: 生成标准化 Task 清单**

按 [references/template.md](references/template.md) 的结构生成最终文档，据此模板逐节填充内容。模板给出完整的章节顺序、字段与示例写法。

### 用户交互策略

- 优先验证用户提供的链接可正常访问。遇到飞书文档时，主动说明将使用 `lark-doc` 读取内容。
- 代码路径较为模糊时，请用户提供精确文件名，或使用 `SearchCodebase` / `Glob` 辅助定位。
- 最终输出为一个 Markdown 文件，放在工作区根目录下。

---

### 核心约束

- 每个 Task 拆分粒度适中，通常 1 个 Task 对应 1 个页面级组件、一个通用组件的升级，或一类相关的状态管理变更。
- 每个 Task 覆盖各自独立的文件集合，Task 之间的文件相互独立。
- 清单只列前端改动点；数据库变更、纯后端配置等由后端方案承载。
- 最终清单中的每个 Task 均属于功能/UI/接口类改动。
- 输出格式与 [references/template.md](references/template.md) 保持一致。
- 开发清单（输出文档）中禁止出现需求文档、技术文档等的链接（含 `file://`、`http(s)://` 等任何协议）；相关出处一律改用文字标注（页面名、路由、接口名、字段名、章节标题）。仅设计稿输入所需的 Figma 链接可保留。
- 最终输出使用中文。
